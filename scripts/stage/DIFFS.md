# Staging versus production

This stack is for a completely invented Mika Tanaka. It never copies production
data. Start it with `scripts/stage/up.sh <clean-checkout-inside-this-clone>`;
use `--flag SETTING_TENANT_IDS=VALUE` for known rollout settings from that
checkout's `config/settings/base.py`. All flags are off unless explicitly supplied.
Run `scripts/stage/down.sh` before starting a second checkout. Host helpers need
Python 3 and Docker; Django and OpenClaw run in Docker. Images are retained by
short git SHA, so rebuild/remove a stage image explicitly after changing its
Dockerfile. Application tracked files must be clean at startup.

| Area | Local difference | Can change assistant behavior? |
| --- | --- | --- |
| OpenClaw image | Built with the chosen checkout's **unmodified** `Dockerfile.openclaw`, including the real 2026.9.4 runtime, bootstrap-cap patch, plugins, CLI tools, entrypoint, proxy and stdout redactor. Local Apple Silicon build rather than the production architecture/build artifact. The Dockerfile has floating Debian/npm dependencies as well as pins. | Possibly: architecture, dependency drift and timing. No stub/model substitution. |
| Django image | `Dockerfile.django` installs application pins from that same checkout on Python 3.12; omits torch/transformers and CUDA/triton packages because there is no neural detector in stage. Uses development settings and gunicorn with one worker/eight threads. Uses the repository gunicorn hooks through default `gunicorn.conf.py` discovery (including detector warm-up/fallback). Skips the production Dockerfile, startup script and ACR model bundle. | Yes: concurrency, startup, detector warm-up and operational behavior. |
| PII detector | No production PII sidecar or baked neural weights. HuggingFace is offline and the model path is deliberately absent. Existing detector failure/fallback behavior remains in application code; it is **not** replaced with a fake detector. Known-value masking and lightweight patterns still run. | **Yes:** neural redaction can fail open or defer authoring; placeholders, receipts and resulting model context can differ substantially. Use synthetic text only. |
| Config and prompts | Real `generate_openclaw_config`, `render_workspace_files`, workspace rules and USER.md envelope via `update_tenant_config`; no hand-written config/prompt files. Stage-only settings replace the existing local-test adapter's Ollama rewrite with a guarded no-op, retaining its filesystem/task seams. Flags-off parity test compares generated bytes with the original adapter disabled. | No new prompt/model rewrite from the stage adapter. Synthetic tenant capabilities/data still determine generated content. |
| Model routing | Starter/default primary and fallback chain come from the checkout's real resolver and local DB state; production model-offer rows are not copied. OpenRouter uses this machine's key rather than a production per-tenant managed key; ZDR/provider routing remains generated by production code. | Possibly: provider availability/account limits/credits, fallbacks and latency. Inspect usage/model logs for the actual selected model. |
| File share | Existing `AZURE_MOCK=true` + `LOCAL_TEST_ROOT` adapter writes through the production sanitize chokepoint to a shared bind mount. Both processes use UID 1000 so atomic 0600 replacements are readable immediately. No Azure SMB, storage-account key, mount delay, storage lease or managed identity. | **Yes:** share latency/failure/permission behavior and races differ. USER.md changes still reach the live container without restart. |
| Network | Own internal Docker network; Django and OpenClaw share a network namespace. The existing synthetic/DEBUG/mock-only `gateway_base_url` loopback seam reaches `127.0.0.1:8080`. The dual-network proxy relays fixed ingress ports to Django/OpenClaw; its random host ports bind only to 127.0.0.1. | Timing/routing failures differ from Azure ingress. No production URL is needed. |
| Egress | Only a CONNECT proxy attached to a second owned network has Internet access. It permits TLS to `openrouter.ai:443` only; runtime containers have no external default route. Node uses its environment proxy support. | **Yes:** weather, search, Reddit, integrations and other outside services cannot work. They fail rather than returning fabricated data. Credentials for Google, LINE, Telegram, Stripe, QStash, APNs, Sentry and Azure are absent. |
| Queue | Real ingress writes `PendingMessage`; the existing QStash-unconfigured local dispatcher invokes the **real production task** through daemon timers after commit. Delays are preserved. No QStash HTTP, delivery signatures, cloud retry durability or recurring control-plane sweeps. | **Yes:** process restart loses timers, scheduling/concurrency/retry characteristics differ. DB queue and drain logic are real. |
| Cron | Real seed builder/refresh service creates canonical `CronJob` rows; real signed-share writer and in-image `nbhd-cron-sync.mjs` install them. `cron.py` runs the named real runtime ID via operator CLI, waits for completion, then reads **all columns** of new `ProactiveOutbound` rows. | **Yes:** manual fire time and no QStash fleet scheduler. Normal container schedules remain enabled while the stack is up and can incur model turns. Delivery may legitimately be suppressed. |
| Chat URL/auth | The chosen main checkout exposes ingress at `/api/v1/chat/messages/`. A stage-only URL alias mounts that **same production view** at the requested `/api/v1/chat/`. Owner access JWTs are issued locally with SimpleJWT; helpers never bypass the HTTP auth/view/queue/poll path. | The alias does not change the view. No real signup/login/refresh UI or device authentication is exercised. |
| Channels | Synthetic iOS channel, normal app message and proactive delivery persistence, no real device token/APNs. No Telegram/LINE links or bot tokens. No live iPhone/calendar sync process. | **Yes:** push timing, notification UX, channel delivery and device sync are untested. `is_synthetic=True`, `is_eval_sink=False`, so eval-sink shortcuts do not replace delivery. |
| Synthetic life | Seven datebook mirror events, active synthetic gateway metadata, five tasks/two overdue, 10K goal, three real daily notes, tax worry, synthetic friendship/project/four canonical steps. Direct models plus normal journal/cron/render services; no real EventKit device registration or sync transport. Datebook and assistant Friends participation are explicitly enabled. Projects v2 follows its real rollout gate: use `--flag PROJECTS_V2_TENANT_IDS=*` to expose the four-step project tools; flags-off has the legacy mission reader. | **Yes:** this is an illustrative life/capability profile, not every default tenant's onboarding state. |
| Database/cache | Private pgvector Postgres 16 and Redis containers/volumes, no Supabase transaction pooler, production role/RLS deployment, Upstash REST, backups or cloud timeouts. Local DB role is the bootstrap superuser. | **Yes:** concurrency, latency, connection/RLS failures differ. Not a production isolation/security test. |
| Hibernation | Container stays running until `down`; no Azure revision lifecycle, waking, scaling, managed identity, resource limits or hibernation sweeps. OpenClaw state is container-local ephemeral storage; bind-mounted share survives only until `down`. | **Yes:** cold starts, session recovery and resource pressure differ. |
| Observability/billing | Production usage plumbing is configured and real chat usage rows were observed; cron usage attribution was not verified. No external telemetry, alerts, billing or live subscription. Mika has a synthetic seven-day trial to pass the real entitlement checks; standard budgets stay active. No production per-tenant key provisioning/cap sync. | Possibly: local budgets/routing can differ; cannot assess production monitoring or billing. |
| Lifecycle | One stack per machine prefix; explicit ownership labels prevent deleting a different worktree's resources. `down` deletes owned containers, both networks, both volumes and `.state` including config, transcripts, DB data and temporary env file. Built images remain. | No long-lived memory across `down`/`up`. |

No application code changes are required. The only process-local adaptation is
in `scripts/stage/settings.py`; it cannot be imported without the explicit
stage/mock environment. Diagnostics, SQL output, messages and cron rows contain
synthetic content. Do not reuse this stack with real user data.
